## Candidate source path and scope

The pinned solve lineage calls microphysics_driver (lines 4482–4720) with `QI_CURR=moist(ims,kms,jms,P_QI)` (4570) and `QNI_CURR=scalar(ims,kms,jms,P_QNI)` (4580). The driver lineage KDM6 case at 2269–2325 passes `QI=qi_curr`, `NI=qni_curr`; the Registry lineage calls them QICE/moist and QNICE/scalar. These are array-slot indices dynamically initialized by WRF, not assumed fixed numeric constants.

After microphysics_driver returns, candidate solve lineage first applies zero_outb to `moist`, then, in the interior, zero_outa to `moist`; parallel calls on scalar/chem/tracer are gated by `mp_zero_out_all>0`. The actual run namelist.output records `MP_ZERO_OUT=2`, `MP_ZERO_OUT_ALL=0`, `MP_ZERO_OUT_THRESH=9.9999999E-09` (a printed float32 representation). The candidate zero-out source describes b as a nonnegative clamp at physical outer edges, and a's mode 2 as a strict `< threshold` assignment to zero for non-vapor fields; vapor is clamped nonnegative. Equality is not zeroed. It is therefore a plausible direct mechanism by which an interior QICE less than threshold is cleared while its QNICE scalar is not processed by these calls. That is not evidence that all QI=0, NI>0 history cells arose this way; negative inputs, dynamics, other processes and previous timesteps matter.

The executable confirms a mode-2 branch at `0x20c95f5`, the load of a scalar at config `+0xe6c` at `0x20c9655`, compare of threshold to data at `0x20c985d`, and zero stores beginning `0x20c98a0` on strict threshold-greater-than-value for ordered finite values. Config mode is read at `+0xe64`. The mode/threshold interpretation is corroborated by source and configuration but must be verified at the trace boundary. `zero_a_*.asm` and `disassembly_receipt.json` retain the excerpts and hashes.

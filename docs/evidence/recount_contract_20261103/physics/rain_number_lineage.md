## Density basis and KDM6 closure

The exact compiled KDM6 driver source takes host `QNRAIN` (`nr`) and forms internal `nrs = nr * den`; on return it stores `nr = nrs / den` (`module_mp_kdm6.f90`, lines 310–318 and 351–355; SHA-256 `c4a7d1e90ea27608ba7efb652cfb79dee2e30db769e076ad1a2e7a7e63d5e52b`). A retained host microphysics source copy passes `DEN=rho` to KDM6, separately from `diag_rhog=rhopo3d` (host `phys/module_microphysics_driver.F`, lines 2535–2551). A retained solver source copy computes its `rho` from `ALT` as `rho = (1 + QVAPOR) / ALT` (`dyn_em/module_big_step_utilities_em.F`, line 4856); the same file sets `ALT = AL + ALB` (line 943). Registry marks `ALT` as inverse density in `m3 kg-1` (Registry.EM_COMMON, line 327). Thus these retained host source files describe a moist-air `rho=(1+QVAPOR)/ALT`, while the diagnostic dry density `1/(AL+ALB)` is `1/ALT`. Algebraically these source formulas differ by `1+QVAPOR`. However, neither the caller nor solver source file is bound to the exact compiled executable, and there is no same-point/same-timestep KDM6 PRE capture here that directly compares runtime `den` to `AL`, `ALB`, and `QVAPOR`. The actual runtime density basis is therefore not directly validated by this investigation.

The Registry metadata for `QNR`/`QNRAIN` is only `# kg-1`; it does not spell out the kilogram basis. The retained Thompson-only `real.exe` source candidate sets `temp_rho = 1./grid%alt`, forms volume concentration from `QRAIN * temp_rho`, and divides by that same `temp_rho` before storing `QNR` (module_initialize_real.F, lines 4811, 4833–4837). Under that source formula, the conversion uses dry-air density. These are distinct source paths and bases; actual runtime execution was not confirmed. The stage-3 diagnostic dry density reconstructed as `1/(AL+ALB)` matches `1/ALT` in the retained solver source, but is not directly proven to be the density used in the compiled KDM6 caller. Do not silently substitute it for `den` in a KDM6 source-equation replay.

This density role is distinct from `diag_rhog`: the retained KDM6 source derives `rhox` from graupel mass and graupel mixing ratio (`qrs(:,:,3)/brs`, lines 3305–3319), then writes that value to `diag_rhog` (line 360). `diag_rhog` is a graupel particle bulk density, not either atmospheric density described above and not the density multiplier for QNRAIN. The source equations establish their own operations; exact runtime density basis and the intended QNRAIN kilogram convention remain unresolved.

KDM6's rain moment closure is two-moment: `QRAIN` alone cannot identify a unique number or particle-size distribution. The retained KDM6 source sets `mur=1.` (line 60) and reconstructs rain intercept from both `nrs` and slope (`n0r=nrs/(rslope*rslopemu*g1pmr)`, lines 1360–1375). Thus the Thompson real-source `make_RainNumber` policy, whose formula uses the exponential/Marshall–Palmer intercept, cannot be transferred directly into the KDM6 path as an asserted physical initializer: its branch is inactive for KDM6, and KDM6 uses a nonzero rain shape parameter. No new coefficient, rain shape, or number seed is proposed here.

For any paired mass/number values with `N > 0`, the bulk mean mass per drop follows `m̄ = q/N` when both are expressed on the same air-mass basis (`q` in kg water per kg air and `N` in drops per kg air). With positive rain mass and zero number, that ratio is undefined; it does not tell us a finite mean drop mass. A PSD assumption or observation constraint must supply the missing information. The source shows one scheme-specific Thompson choice, but it does not establish an intended KDM6 initializer.

## Smallest justified next experiment and blocker

The smallest useful next step is a read-only, build-bound provenance capture for the historical CP02 `real.exe`: hash the precise host source files and registry/configuration from the `cp02_host_process_domain_fm547n5i` build, and bind them to the recorded executable/build receipt. Keep the historical CP02 OFF/HYDRO/LIQUID inputs separate from current recount B1 (`ORIGINAL_B1_100`). For B1, bind its actual input-producing writer and effective namelist before making an initializer claim; then use a same-point, same-timestep KDM6 PRE capture if runtime `den` must be compared with input `AL`, `ALB`, and `QVAPOR`. The retained stage-3 probe binds the KDM6 executable and selected call-entry values for historical HYDRO, but it does not bind current B1 provenance or runtime density for B1.

If an initializer is proposed after this provenance step, the next minimal runtime experiment should compare the same historical inputs through the pinned KDM6 executable with and without one explicitly justified PSD-consistent number initialization, recording paired QRAIN/QNRAIN at first call and coupled rain, vapor, and temperature tendencies/budgets. Do not use `nrmin` as an initializer by itself: it is a process threshold, not a PSD observation. Do not claim the Thompson source rule applies to KDM6.

The source/build binding is the blocker to an exact statement of what the historical `real.exe` did. Present score evidence continues to show no qualified candidate and a weak/low CSI tradeoff; this lineage review does not change scores or claim candidate qualification.

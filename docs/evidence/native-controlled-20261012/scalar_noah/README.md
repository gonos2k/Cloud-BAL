# Paired Noah scalar diagnostic (2026-10-12)

This is a separate compile diagnostic, not the FTZ/DAZ policy-causality pair. It recompiles both Noah objects together from the preserved PR61 partial-host source with the pinned strict O0 profile plus `-no-vec`, then links each runtime arm from the same resulting executable. All other objects, main source, inputs, and `-fpe0` exception handling remain fixed. The two runtime arms only differ by setting MXCSR FTZ and DAZ before `wrf_init` in the `ftz_daz` arm.

Both Noah source files compiled cleanly. The resulting model starts past Noah LSMINIT in both arms and enters KDM6 initialization. It does not complete that initialization: both runs trap with SIGFPE divide-by-zero at `module_mp_radar_mp_radar_init_+3747`, instruction `divss (%rax),%xmm0`. This closes the Noah startup blocker only for this scalar diagnostic; it is not a successful native run and does not validate KDM6 or the candidate.

The canonical preserved PR61 `.F` sources are unchanged (driver SHA256 `6351d154581d2ca5a5fa0e013fd6519c6f3accc3e5ef84184facb35c053c113f`; LSM SHA256 `9371a55d224aba85c8b35a0bdf55d2e5d3139679ab1a4e2c17f873a2b59864a9`). The actual `.f90` inputs named on the compiler argv are the preserved generated/preprocessed forms (driver SHA256 `eff3c4f13662ce01ddc9c49c3b345687451f91b01783d771ad129be8e5a886fb`; LSM SHA256 `73c2eb1384e93426570edf040a970f9ea2ae0849d71ec4ea3d36296514af2e7a`). Both changed objects are compiled together with the pinned strict O0 profile plus `-no-vec`, retaining `-fpe0`. The inherited Noah object compile flags are not fully certified in this evidence, so the comparison does not isolate the outcome to `-no-vec` alone. It establishes that the preserved source rebuilt in this combined diagnostic profile removes the observed Noah `divps` trap and passes Noah initialization; it does not prove that vectorization by itself caused the trap. The final frozen two-arm scalar pair contains exactly two WRF starts; the one-driver-only and initial two-object debugging probes each contributed one captured gradual WRF start before the paired rerun. One additional GDB replay of the same gradual scalar executable captured the scalar denominator and performed no build. None reached time integration. A separate debugger replay on the gradual scalar arm captured the downstream operands exactly: `divss (%rax),%xmm0` at `0x2696763`, `$rax=0x7b6c840` (`module_mp_radar_mp_xam_g`), memory `0x00000000`, and XMM0 `0x3f800000` (1.0). MXCSR has the divide-by-zero status bit set; this is a divide-by-zero trap, not invalid. The source maps to `radar_init`, `module_mp_radar.F` lines 181-183 (`xoamg = 1./xam_g`). KDM6 initialization sets `xbm_g` and `xmu_g`, but does not set `xam_g` before `radar_init`; later KDM6 reflectivity code reads `xam_g(k)` (line 3976), so this is an unresolved coefficient initialization contract, not an unused coefficient. Do not treat the trap as permission to invent a coefficient. See `radar_operands_gdb.log`, `radar_source_excerpt.txt`, and pinned source `/var/tmp/pr61_ccn_origin_20261006/hostcopy/phys/module_mp_radar.F` and `module_mp_kdm6.F` for evidence.

# Whole KDM6 local-column replay

`run.sh` builds the pinned CONTROL source and the source with the write-only probes generated by `prepare.py`. It checks the exact source SHA-256 and the listed dependency hashes, compiles each build with the pinned Intel O0 and O2 profiles in a new scratch directory, runs 15 inputs (five 39-level columns, three ice-number seeds), and compares every terminal binary byte between the original and instrumented builds at each optimization. All 30 comparisons passed. A second fresh invocation reproduced every saved terminal and stage file byte-for-byte. The O0 and O2 stage files are also byte-identical for these cases. This is a standalone local-column experiment, not a WRF forecast or an observation of the first microphysics call.

Inputs are generated from `cases/profiles.json` (SHA-256 `e1024d0792b3a9db313d1e00e8d966ec7b7bdbb4573684a14aa398a07def08ca`). Each seed changes only NI within the same case. File-derived density and DELZ are proxies, not captured runtime arrays. TH is file perturbation T plus 300 K, and PII is derived as dry_tk/TH; this ratio reproduces the chosen temperature in the driver but is not a captured native PII. Pressure is P+PB, and BG is the file QIB without an added floor. The script preserves input text and its case map under `results/inputs/`.

The chosen experiment parameters include DELT=20 s, NCMIN_LAND=NCMIN_SEA=10 m-3, CCN0=2e8, SCALE_H=0, land and sea NN multipliers 1, radar and diagnostic flags off, and ITIMESTEP=2. QMIN is the pinned host caller's epsilon=1e-15, not a measurement of a live model call. The caller passes the other thermodynamic constants from `module_model_constants`, and the driver uses that pinned module. Other call choices are shown explicitly in `driver.f90`.

Every `stages.txt` row contains stage name, loop, i, k, QI (kg kg-1), NI (m-3), density (kg m-3), a stage-specific value, and temperature (K). The stage-specific value is -1 except for SLOPE (the actual REAL32 inverse lambda in metres) and PSD1/2/3_ACTIVE (the actual selected REAL32 `lamdi_tmp` in m-1). PRE and POST appear even if the branch is inactive; ACTIVE appears only inside the branch. WRAPPER is after kg-1 to m-3 conversion, ENTRY after the entry clamp, SLOPE after the first slope call, and FINAL after wrapper conversion back to kg-1 (the record retains internal m-3 NI). PSD stages occur in source order, including intervening real routine operations. Stage input thresholds are QMIN=1e-15 and NCMIN=10 for this experiment. Loop values are zero for wrapper/entry/final and actual loop numbers elsewhere.

Each `terminal.bin` is a native little-endian Intel stream of 827 REAL32 values (3308 bytes), in this Fortran array order: TH, Q, QC, QR, QI, QS, QG, NN, NC, NI, NR, BG, DIAG_RHOG, DEN, PII, P, DELZ (39 values each), XLAND, RAIN, RAINNCV, SNOW, SNOWNCV, SR, GRAUPEL, GRAUPELNCV (one each), REFL, RE_CLOUD, RE_ICE, RE_SNOW (39 each). Exact comparison covers every public state array and precipitation/diagnostic output passed by the driver. The original source and the instrumented source both use a rank-zero WRF rank stub, provided in the driver, and the supplied radar/runtime fixtures; this does not establish native host integration.

The pinned CONTROL hash is `f391b211c6e111f92a7213cc5a651606ec6b5826a47063e3057ab2d819e9a595`. The host radar snapshot hash is `5f24e3b5a74dd26499faf1f0bb69b8e7b05e87a56b4746fbfe4fca110020b6b7`; module constants `5b80377fecdc18a5f0ad38d3b6c15cfc86ad5d76701adbbbb08a08698d0f7062`. Remaining fixture hashes and compiler identity checks are enforced in `run.sh` and `tests/intel_toolchain.sh`. The generated full instrumented source is retained in `results/instrumented.f90`, so all inserted writes can be reviewed against CONTROL. `summary.json` records per-case terminal and stage hashes and aggregate counts.

# Matched native first-call row

The CONTROL executable is the previously built activation-path CONTROL. Its build receipt pins the insertion-only source `CONTROL.f90` SHA256 `f391b211c6e111f92a7213cc5a651606ec6b5826a47063e3057ab2d819e9a595` and executable `3a286f6691fa94c2dccf55b14e4cbf609b8c9540c2caf83556969932ca9854ea`. The instrumentation selects other columns and times; this capture uses GDB to read the existing executable's KDM6 ABI, with no inferior data writes. Software breakpoints are used. The CONTROL executable is not the historical B1 executable.

`capturedsmallrecords/rank3.jsonl.gz` holds the first KDM6 wrapper entry and return for the row containing (192,72): `i=118..233`, `j=72`, `k=1..39`. Each JSON line has `event`, `cell`, full domain/memory/tile `bounds`, `step`, `bases`, `options` and `fields`. Each field contains its IEEE binary32 little-endian bytes as `hex_le`, decoded decimal `value`, and effective memory `pointer`. Pointers are process-specific and serve identity auditing, not replay inputs. Scalars and 2D fields repeat per level. The GDB script records all wrapper state arguments, density, thickness, pressure, Exner, land, surface precipitation, physics constants and option flags. It does not record the internals of KDM62D or sedimentation; those require a replay.

`receipt.json` records exact hashes, dimensions and parity. All three runs used the same matched executable and private copies of the frozen 89 inputs, with namelist changed to 80 s and terminal history. Normal execution and both GDB captures produced byte-identical initial and +80 s histories. Both capture versions also agreed bit-for-bit on every shared field at every row point. This is a scoped observation of execution parity, not runtime or scientific validation beyond this case. Large histories remain outside the repository. `stage.py`, `run_pair.sh`, `run_options.sh` and `rank_wrapper.sh` retain the local procedure and paths; these depend on the external frozen inputs, executable, and Intel/MPI profile.
